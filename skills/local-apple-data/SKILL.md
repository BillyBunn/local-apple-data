# Local Apple Data

Use the `local-apple-data` MCP server for the user's locally synced Mail.app mail, Messages chats, inferred Hide My Email aliases, Voice Memos, Safari bookmarks/Reading List/folder metadata, Shortcuts metadata/selected-folder shortcut metadata, Apple Books metadata/annotations, Apple Podcasts metadata, Apple Music metadata, Apple TV metadata, Apple Freeform metadata, Apple Notes note/folder/selected-folder item metadata, Apple Calendar, Apple Contacts, Apple Photos asset/regular-album/selected-album metadata and regular-album management, Apple Reminders, and iCloud Drive files. Do not use the Gmail connector, Gmail API, IMAP, OAuth, app passwords, iCloud.com, browser sessions, keychain credentials, private iCloud web APIs, or network mail access for these workflows unless the user explicitly asks for those external paths.

## Completion And Handoff Standard

- For fresh sessions, project-status requests, publication checks, or broad completeness claims, verify the live repo/plugin state before making claims.

## Workflow

1. Start with `apple_data_health` or `apple_data_doctor` if current local readiness has not been checked in this session.
2. Use narrow, user-requested searches only. Do not run broad dumps or empty searches.
3. Keep limits small unless the user asks for a larger result set.
4. Treat search results as local metadata that may include subjects, Messages chat display names, inferred Hide My Email alias previews, Voice Memo titles, Safari bookmark titles/domains and folder titles, Shortcuts names, Books titles/authors/genres, Podcasts show titles/authors/categories/providers, Music track/artist/album/genre and playlist names, TV item/show/artist/genre and playlist names, Freeform board recency/count metadata and folder titles, note titles/snippets, calendar event titles, contact names/organizations, Photos filenames, iCloud Drive filenames, or reminder titles. Summarize only the minimum useful facts in chat.
5. Use exact opaque handles from search results for metadata fetches. Do not fabricate handles or retry old raw row-ID handles.
6. If the user asks for Mail message content and you are selecting from search results, prefer a result whose `content_status` is `available`. Treat `unavailable` or `unknown` as a reason to skip that handle or report that local content may not be retrievable.
7. Use `mail_search_body`, `mail_search_advanced`, or `mail_search_attachments` only for narrow Mail discovery with an explicit `after` or `before` date bound. These tools return capped redacted snippets, masked header metadata, or attachment filename/MIME/text/PDF/OCR snippet metadata only; they do not return full message bodies or attachment bytes. Use `include_content` for attachment text/PDF snippets and `include_ocr` only when OCR fallback is needed.
8. Use `mail_build_fts_index` / `mail fts-build` only when the user asks for audit-grade Mail discovery over a bounded date range and accepts the private local cache. Build requires `confirm_index=true` / `--confirm-index` because it writes a durable local FTS cache that may contain extracted subject/header/body text and optional attachment text; large bounded builds must follow `next_cursor`, and `reset` is allowed only on the first build page. Use `mail_search_fts` / `mail fts-search` only with date bounds; it returns exact handles plus capped redacted snippets after live-row/date/content-state revalidation, not full bodies, attachment bytes, cache paths, or raw cached text.
9. Call `mail_get_content` only on an exact `mail:message:v2:` handle the user selected, provided, or approved from metadata or discovery results. Keep `max_chars` bounded; use 4000 unless the user asks for a smaller limit, never above 12000, and follow `next_offset` when paging a long selected message.

Treat only `classification:one_click` as eligible for an RFC 8058 POST. Every `manual_required`, `classification:body_link`, and `action:help` endpoint requires separate handling and must never be auto-posted.
